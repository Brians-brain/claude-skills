# 加深（Deepening）

如何在既有依賴下，安全地加深一群淺模組。使用 [SKILL.md](SKILL.md) 中的詞彙：**模組**、**介面**、**seam**、**轉接器**。

## 依賴分類

評估一個加深候選時，先把它的依賴分類。分類決定了加深後的模組要如何跨越 seam 測試。

### 1. 行程內（In-process）

純運算、記憶體內狀態、沒有 I/O。一定可以加深：把模組合併，直接透過新介面測試。不需要轉接器。

### 2. 可在本地替代（Local-substitutable）

有本地測試替身的依賴（例如用 SQLite 記憶體資料庫代替正式資料庫、用 pytest 的 `tmp_path` 代替真實檔案目錄）。只要替身存在就可以加深。加深後的模組在測試中搭配替身執行。seam 是內部的；模組的外部介面上沒有 port。

### 3. 遠端但自有（Ports & Adapters）

跨越網路邊界的自有服務（微服務、內部 API）。在 seam 上定義一個 **port**（介面）。由 deep module 擁有邏輯；傳輸方式以**轉接器**注入。測試使用記憶體內的轉接器，正式環境使用 HTTP／gRPC／佇列轉接器。

建議的說法：「_在 seam 上定義一個 port，正式環境實作 HTTP 轉接器、測試實作記憶體內轉接器，讓邏輯留在同一個 deep module 中，即使它是跨網路部署的。_」

### 4. 真正的外部（Mock）

你無法控制的第三方服務（經銷商報價 API、匯率 API、寄信服務等）。加深後的模組以注入的 port 接收外部依賴；測試提供 mock 轉接器。

## Seam 紀律

- **一個轉接器代表假想的 seam，兩個轉接器才是真的 seam。** 除非至少有兩個轉接器說得過去（通常是正式環境＋測試），否則不要引入 port。只有一個轉接器的 seam 只是多一層間接。
- **內部 seam 與外部 seam。** deep module 可以有內部 seam（實作私有、供自己的測試使用），也有位於介面上的外部 seam。不要只因為測試會用到，就把內部 seam 透過介面暴露出去。

## 測試策略：取代，而非疊加

- 一旦在加深後的模組介面上有了測試，淺模組上的舊單元測試就成了浪費；刪掉它們。
- 在加深後的模組介面上寫新測試。**介面就是測試面。**
- 測試透過介面對可觀察的結果做斷言，而不是對內部狀態。
- 測試應該能撐過內部重構，因為它們描述的是行為而非實作。如果實作一改，測試就得跟著改，代表它越過了介面在測試。
