# 診斷 Bug

全程使用繁體中文與使用者溝通。

這是處理難纏 bug 的紀律。除非有明確理由，否則不要跳過任何階段。

探索程式碼時，若有 `GLOSSARY.md` 就先讀，建立相關模組的清楚心智模型；也要查看你所修改區域裡的 ADR。

## 遮蔽機密

這個 skill 會要你展示指令、輸出與擷取到的資料。**先遮蔽所有機密**：把它換成 `<REDACTED>`。迴圈要以環境變數建構，讓憑證留在環境裡，而不是出現在你展示的內容裡。擷取到的資料常帶有認證 header（例如經銷商 API key）：只引用帶有訊號的那幾行。

如果遮蔽後的輸出不足以診斷，就直說，並詢問使用者。

## 階段 1：建立回饋迴路

**這就是這個 skill 的核心。** 其他都是機械性的工作。只要你有一個針對**這個** bug 的**緊密** pass/fail 訊號（會因為這個 bug 而變紅），你就一定找得到原因；二分搜尋、假設驗證、插樁觀察，都只是在消費這個訊號。如果沒有，盯著程式碼看再久也救不了你。

在這裡投入不成比例的心力。**積極、有創意、絕不放棄。**

### 建立迴路的方法（大致依此順序）

1. **失敗的測試**：在能觸及 bug 的任何 seam 上（單元、整合、端對端），例如 `pytest tests/test_x.py::test_bug -q`。
2. **HTTP 腳本**：用 `curl` 或一小段 `requests` 腳本打正在執行的服務。
3. **CLI 呼叫**：用固定的輸入檔（fixture，例如一份縮小的 BOM Excel）執行，並把 stdout 或輸出檔和已知正確的快照做 diff。
4. **無頭瀏覽器腳本**（Playwright）：操作 UI，並對 DOM、console、網路請求做斷言。
5. **重播擷取的資料**：把真實的 API 回應、payload、事件紀錄存到磁碟（例如經銷商 API 的 JSON 回應），再單獨把它餵進該程式路徑。
6. **拋棄式測試架**：只啟動系統的最小子集（一個模組、依賴用假的），用一次函式呼叫就能觸發 bug 路徑。
7. **性質測試／模糊測試迴圈**：如果 bug 是「有時候輸出錯誤」，跑 1000 組隨機輸入找出失敗模式（可用 `hypothesis`）。
8. **二分搜尋測試架**：如果 bug 出現在兩個已知狀態之間（commit、資料集、套件版本），把「切到狀態 X、檢查、重複」自動化，就能用 `git bisect run`。
9. **差異比對迴路**：同一份輸入分別跑舊版與新版（或兩種設定），比對輸出差異。
10. **人在迴路中的 bash 腳本（HITL）**：最後手段。如果必須由人去點擊，就用 `scripts/hitl-loop.template.sh` 引導**人**操作，讓迴路仍然結構化。擷取到的輸出會回傳給你。

建對回饋迴路，bug 就修好了九成。

### 收緊迴路

把迴路當成產品來打磨。有了**一個**迴路之後，把它**收緊**：

- 能更快嗎？（快取前置作業、略過無關的初始化、縮小測試範圍。）
- 訊號能更銳利嗎？（斷言具體症狀，而不是「沒有當掉」。）
- 能更確定嗎？（固定時間、固定亂數種子、隔離檔案系統、凍結網路。）

一個 30 秒又不穩定的迴路，只比沒有好一點；一個 2 秒且結果確定的迴路才叫緊密，那是除錯的超能力。

### 非確定性的 bug

目標不是乾淨的重現，而是**更高的重現率**。把觸發條件跑 100 次、平行化、加壓、縮小時間窗、插入 sleep。50% 機率出現的 bug 可以除錯，1% 不行，所以要持續提高重現率，直到可以除錯為止。

### 真的無法建立迴路時

停下來並明確說出來。列出你試過的方法。向使用者要：(a) 能重現問題的環境存取權，(b) 遮蔽過的擷取資料（log、輸入檔、帶時間戳的螢幕錄影），或 (c) 加上暫時性觀測紀錄的許可。**沒有迴路，就不要進入假設階段。**

### 完成條件：一個會變紅的緊密迴路

當迴路**緊密**且**能變紅**時，階段 1 才算完成：你能指出**一個指令**（腳本路徑、測試呼叫、curl），而且你**已經實際執行過至少一次**（附上遮蔽後的指令與輸出），並且它：

- [ ] **能變紅**：它走的是真正的 bug 程式路徑，並斷言**使用者描述的那個症狀**，所以它會因這個 bug 變紅、修好後變綠。不是「執行沒有出錯」，它必須能**抓到這個特定 bug**。
- [ ] **確定性**：每次跑結果都一樣（不穩定的 bug：要有固定且夠高的重現率，見上文）。
- [ ] **快速**：秒級，不是分鐘級。
- [ ] **Agent 可自行執行**：你能無人看管地跑它；只有透過 `scripts/hitl-loop.template.sh` 才讓人介入。

如果你發現自己在這個指令還不存在時就開始讀程式碼、建立理論，**停下來：直接跳到假設，正是這個 skill 要防止的失敗模式。** 沒有能變紅的指令，就沒有階段 2。

## 階段 2：重現與最小化

執行迴路，看著它在 bug 出現時變紅。

確認：

- [ ] 迴路產生的是**使用者**描述的失敗模式，而不是剛好在附近的另一個失敗。抓錯 bug，就會修錯地方。
- [ ] 失敗可以在多次執行中重現（非確定性 bug：重現率高到足以除錯）。
- [ ] 你已擷取到確切的症狀（錯誤訊息、錯誤輸出、慢的時間），讓後續階段能驗證修正確實解決了它。

### 最小化

變紅之後，把重現縮小到**仍會變紅的最小情境**。輸入、呼叫端、設定、資料、步驟，**一次只砍一項**，每砍一項就重跑迴路，只保留對失敗有承重作用的部分。

為什麼要做：最小重現能縮小階段 3 的假設空間（剩下可疑的零件更少），也會成為階段 5 乾淨的回歸測試。

完成條件：**剩下的每個元素都有承重作用**，拿掉任何一個，迴路就會變綠。

在完成重現**與**最小化之前，不要往下走。

## 階段 3：提出假設

在驗證任何一個之前，先產出 **3–5 個排序過的假設**。只想一個假設，會被第一個看似合理的想法綁住。

每個假設都必須**可被否證**：寫出它的預測。

> 格式：「如果原因是 <X>，那麼改變 <Y> 會讓 bug 消失／改變 <Z> 會讓它更嚴重。」

寫不出預測的假設只是直覺：丟掉，或把它磨利。

**驗證之前，先把排序後的清單給使用者看。** 使用者常有領域知識能立刻重新排序（「#3 那裡我們剛改過」），或知道哪些假設已經排除。這是便宜又省時的檢查點。不要因此卡住：如果使用者不在，就照你的排序繼續。

## 階段 4：插樁觀察

每一個探針都必須對應階段 3 的某個具體預測。**一次只改變一個變數。**

工具偏好：

1. **除錯器／REPL 檢查**（`breakpoint()`、`pdb`），只要環境支援。一個中斷點勝過十行 log。
2. 在能區分不同假設的邊界上加**有針對性的 log**。
3. 絕不「全部印出來再 grep」。

**每一行除錯 log 都要加上唯一前綴**，例如 `[DEBUG-a4f2]`。最後清理時只要 grep 一次。沒有標記的 log 會殘留下來；有標記的 log 才會被清掉。

**效能分支。** 對於效能退化，log 通常不是對的工具。改為：先建立基準量測（計時測試架、`time.perf_counter()`、`cProfile`、SQL 查詢計畫），再做二分搜尋。先量測，再修正。

## 階段 5：修正與回歸測試

**修正之前**先寫回歸測試，但前提是有**正確的 seam**。

正確的 seam 是指：測試能重現 bug 在呼叫端實際發生時的**真實模式**。如果唯一可用的 seam 太淺（bug 需要多個呼叫端，測試卻只有單一呼叫端；或單元測試無法重現觸發 bug 的那條呼叫鏈），在那裡寫回歸測試只會帶來虛假的信心。

**如果沒有正確的 seam，這本身就是一個發現。** 記下來：程式架構讓這個 bug 無法被鎖住。把這件事提給使用者。

如果有正確的 seam：

1. 把最小重現變成該 seam 上會失敗的測試。
2. 看著它失敗。如果你是靠修改程式碼或 fixture 來製造紅燈，要和未修改的原版做 `diff`，證明修改確實生效，再相信這個結果。
3. 套用修正。
4. 看著它通過。
5. 用原始（未最小化）的情境重跑階段 1 的回饋迴路。

## 階段 6：清理

宣告完成之前必須做到：

- [ ] 原始重現不再發生（重跑階段 1 的迴路）
- [ ] 回歸測試通過（或已記錄為何沒有合適的 seam）
- [ ] 所有 `[DEBUG-...]` 插樁都已移除（grep 前綴確認）
- [ ] 拋棄式原型已刪除（或移到明確標示的除錯位置）
- [ ] 最後被證實的那個假設寫進 commit 或 PR 訊息，讓下一個除錯的人學到
