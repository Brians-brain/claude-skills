# ADR 格式

ADR 放在 `docs/adr/`，依序編號：`0001-slug.md`、`0002-slug.md`，依此類推。

`docs/adr/` 目錄採延遲建立：需要第一份 ADR 時才建立。

## 範本

```md
# {決策的簡短標題}

{1–3 句話：背景是什麼、決定了什麼、為什麼。}
```

就這樣。一份 ADR 可以只有一段話。它的價值在於記錄「**曾經**做過這個決策」以及「**為什麼**」，而不是把各個欄位填滿。

## 選用段落

只有在真正有價值時才加。大多數 ADR 用不到。

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：決策會被重新檢討時有用
- **考慮過的方案**：只有當被否決的方案值得記住時
- **後果**：只有當有不明顯的下游影響需要點出時

## 編號

掃描 `docs/adr/` 找出目前最大的編號，加一。

## 什麼時候提議 ADR

以下三點必須**同時成立**：

1. **難以反悔**：之後改變主意的成本很高
2. **沒有背景就會覺得奇怪**：未來的讀者看到程式碼會想「他們到底為什麼要這樣做？」
3. **真實取捨的結果**：當時確實有其他可行方案，而你基於特定理由選了其中一個

決策容易反悔就跳過，反正改回來就好。不令人意外就跳過，沒人會好奇。沒有真正的替代方案也跳過，除了「我們做了顯而易見的事」之外沒什麼好記。

### 哪些值得記錄

- **架構形狀。**「資料抓取與成本計算拆成兩個獨立模組，中間只用 CSV 交換。」
- **context 之間的整合方式。**「Sourcing 與 Costing 之間只透過檔案交換資料，不互相 import。」
- **有綁定成本的技術選擇。** 資料庫、外部資料來源、部署方式。不是每個函式庫都算，只算那些換掉要花一季的。
- **邊界與範圍決策。**「價格資料只以經銷商 API 為準，不採用人工輸入的報價。」明確說「不做」的部分和「要做」的一樣有價值。
- **刻意偏離常規的做法。**「我們用原生 SQL 而不用 ORM，因為 X。」凡是一般讀者會以為相反的地方都算。這能防止下一個工程師把刻意的設計「修好」。
- **程式碼裡看不到的限制。**「因為客戶合約，報價必須以新台幣計並保留到小數第二位。」「經銷商 API 每分鐘最多 30 次請求。」
- **否決理由不明顯的方案。** 如果考慮過直接爬網頁、最後選擇官方 API 是有微妙理由的，就記下來；否則半年後又會有人提議改用爬蟲。
