# 改善程式碼架構

與使用者溝通、以及 HTML 報告的內容，都使用繁體中文（`<html lang="zh-Hant">`）；架構術語依 `codebase-design` 的中英對照使用，程式碼識別名稱維持原文。

找出架構上的摩擦，並提出**加深的機會**：把淺模組變成深模組的重構。目標是可測試性與 AI 可理解性。

這個指令以專案的領域模型為**依據**，並建立在一套共同的設計詞彙上：

- 用 Skill tool 呼叫 "codebase-design"，取得架構詞彙（**模組**、**介面**、**深度**、**seam**、**轉接器**、**槓桿**、**局部性**）與其原則（刪除測試、「介面就是測試面」、「一個轉接器＝假想的 seam，兩個＝真的」）。每個建議都精確使用這些術語，不要飄移成「元件」「服務」「API」或「邊界」。
- `GLOSSARY.md` 中的領域語言為好的 seam 命名；`docs/adr/` 中的 ADR 記錄了這個指令不應該重新爭論的決策。

## 流程

### 1. 探索

**掃描之前先劃定範圍：YAGNI。** 加深一個模組的回報，在於讓之後對它的修改變容易，所以要特別重視最近有變動的部分。在看之前，先決定要看**哪裡**：

- 如果使用者指出了方向（某個模組、子系統、痛點），就照著走，並跳過下方的推斷。
- 否則，往回看一大段 commit 歷史（`git log --oneline`），找出程式碼的熱點：一再出現的檔案與區域，讓這些路徑優先吸引你的注意力。如果變動很分散、沒有明顯熱點，就把網撒大一點。

先讀專案的領域術語表（`GLOSSARY.md`），以及你要碰的區域裡的任何 ADR。

然後派一個子 agent 走過整個程式碼。不要照死板的經驗法則；有機地探索，並記下你在哪裡感到摩擦：

- 哪裡要理解一個概念，必須在許多小模組之間來回跳？
- 哪裡的模組是**淺**的，介面幾乎和實作一樣複雜？
- 哪裡為了可測試性抽出了純函式，但真正的 bug 藏在它們被呼叫的方式裡（沒有**局部性**）？
- 哪裡緊密耦合的模組越過 seam 互相洩漏？
- 程式碼的哪些部分沒有測試，或很難透過目前的介面測試？

對任何你懷疑是淺的東西套用**刪除測試**：刪掉它，複雜度會集中，還是只是搬家？「會，複雜度會集中」就是你要找的訊號。

### 2. 以 HTML 報告呈現候選

把一個自給自足的 HTML 檔寫到作業系統的暫存目錄，讓 repo 裡不會多出任何東西。從 `$TMPDIR` 取得暫存目錄，沒有就用 `/tmp`（Windows 用 `%TEMP%`），寫到 `<tmpdir>/architecture-review-<timestamp>.html`，讓每次執行都產生新檔。幫使用者打開它（Linux 用 `xdg-open <path>`、macOS 用 `open <path>`、Windows 用 `start <path>`），並告訴他絕對路徑。

報告用 **CDN 版 Tailwind** 處理版面與樣式，在圖形／流程／序列能可靠表達結構的地方，用 **CDN 版 Mermaid** 畫圖。把 Mermaid 和手工 CSS／SVG 視覺混著用：關係是圖形狀的（呼叫圖、相依、序列）時用 Mermaid；想要更有編輯感的東西（質量圖、剖面圖、收合動畫）時用手工 div／SVG。每個候選都要有一張**之前／之後的視覺化**。要視覺化。

每個候選渲染成一張卡片，包含：

- **檔案**：牽涉哪些檔案／模組
- **問題**：目前的架構為什麼造成摩擦
- **解法**：白話描述會改變什麼
- **好處**：以局部性與槓桿來說明，以及測試會如何改善
- **之前／之後圖**：並排、自己畫，呈現淺的現況與加深後的樣子
- **建議強度**：`強烈建議`、`值得探索`、`推測性` 其中之一，以徽章呈現

報告最後是一個**首要建議**段落：你會先處理哪個候選、為什麼。

**領域用 GLOSSARY.md 的詞彙，架構用 `/codebase-design` 的詞彙。** 如果 `GLOSSARY.md` 定義了「替代料」，就說「替代料篩選模組」，而不是「FooBarHandler」，也不是「替代料服務」。

**ADR 衝突**：如果某個候選和既有的 ADR 矛盾，只有當摩擦真實到值得重新檢討那份 ADR 時才提出來。在卡片中清楚標示（例如一個警告框：「_與 ADR-0007 矛盾，但值得重新討論，因為……_」）。不要列出 ADR 禁止的每一個理論上的重構。

完整的 HTML 骨架、圖形樣式與排版指引，見 [HTML-REPORT.md](HTML-REPORT.md)。

**還不要**提出介面。檔案寫好之後，問使用者：「你想探索其中哪一個？」

### 3. 拷問迴圈

使用者選定一個候選後，用 Skill tool 呼叫 "grilling"，和他一起走過決策樹：限制、相依、加深後模組的形狀、seam 背後放什麼、哪些測試能留下來。

副作用隨著決策成形當場發生；用 Skill tool 呼叫 "domain-modeling"，邊走邊讓領域模型保持最新：

- **用一個不在 `GLOSSARY.md` 裡的概念為加深後的模組命名？** 把這個術語加進 `GLOSSARY.md`。檔案不存在就延遲建立。
- **在對話中磨利了一個模糊的術語？** 當場更新 `GLOSSARY.md`。
- **使用者以一個有分量的理由拒絕了這個候選？** 提議寫一份 ADR，說法是：「_要我把這記錄成 ADR，讓之後的架構審查不會再提出它嗎？_」只有當未來的探索者真的需要這個理由才能避免重提同一件事時才提議；短暫的理由（「現在不值得」）和不言自明的理由就跳過。
- **想為加深後的模組探索不同的介面？** 用 Skill tool 呼叫 "codebase-design"，使用它的「設計兩次」平行子 agent 模式。
