# 邏輯原型

一個獨立、自給自足的 HTML 檔（一份**可分享的展示**），讓任何人都能透過點按鈕來操作一個狀態模型。當問題是關於**商業邏輯、狀態轉換或資料形狀**時使用：那種在紙上看起來合理、但一推過真實案例就覺得不對勁的東西。

因為它只是一個檔案、不用安裝任何東西，你可以把它交給非開發者（採購、業務、PM、領域專家），讓他們自己感受這個模型。所以它要說他們的語言，而不是程式碼的語言。

## 什麼時候該用這個形狀

- 「我不確定這個狀態機能不能處理先 X 再 Y 的邊角情況。」
- 「這個資料模型真的能表示……的情況嗎？」（例如：同一顆料有多個替代料、其中一個又停產）
- 「在動手寫之前，我想先感受一下 API 該長什麼樣子。」
- 任何有人想要**按按鈕、看狀態變化**的情況。

如果問題是「這個該長什麼樣子」，那就是走錯分支了。改用 [UI.md](UI.md)。

## 流程

### 1. 寫明問題

寫程式之前，先寫下你要模擬的是什麼狀態模型、要回答什麼問題。一段話，放在展示的最上方（放在看得到的介紹區，不只是註解）。回答錯問題的邏輯原型完全是浪費，所以要把問題寫明確，讓之後可以檢查，不論使用者是現在在看，還是之後才回來看。

### 2. 把邏輯隔離成可攜的模組

把真正的邏輯（回答問題的那一部分）放在單一 `<script>` 區塊中，寫成一個小而純的模組，之後可以直接拿出來放進正式程式碼。周圍的頁面是拋棄式的，這個模組不是。

正確的形狀取決於問題：

- **純 reducer**：`(state, action) => state`。適合動作是離散事件、狀態是單一值的情況。
- **狀態機**：明確的狀態與轉換。適合「現在哪些動作是合法的」本身就是問題一部分的情況。
- **一小組純函式**，作用在一個單純的資料型別上。適合沒有隱含的「目前狀態」、只有轉換的情況。
- **一個有清楚方法介面的類別或模組**，當邏輯確實擁有持續的內部狀態時。

選最符合所問問題的形狀，**而不是**最容易接到頁面上的形狀。保持純粹：不碰 DOM、不碰 `document`、不讓按鈕處理函式伸進它內部。頁面呼叫它；不會有東西反向流動。這就是讓原型在自身生命週期之後仍然有用的原因：問題一旦得到答案，驗證過的 reducer／狀態機／函式集就能自己被搬進正式模組。

如果正式程式碼是 Python，在展示頁面旁邊另外附上同一份邏輯的 Python 版本（純函式，不依賴任何框架），並確保兩者行為一致。

### 3. 建立可分享的 HTML 檔

一個檔案，純 HTML／CSS／JS：不用框架、不用打包工具、不用伺服器，所有東西都寫在檔案內，雙擊就能開，用 email 傳來傳去也不會壞。任何人打開就能執行。

為非開發者撰寫。每個標籤都使用**領域語言**，而不是程式碼：按鈕和狀態讀起來要像業務本身，而不是 reducer。用白話說明正在發生什麼。

用清楚的層次由上而下排版：

1. **標題與一行說明**：這份展示讓你探索什麼（步驟 1 的問題）。
2. **目前狀態**：完整的相關狀態，以易讀的面板呈現（有標籤的欄位，不是原始 JSON），每次點擊後重新顯示，讓變化看得見。如果有助於非開發者理解，標出剛剛改變了什麼。
3. **自由操作按鈕**：每個動作一個按鈕，永遠可用，讓任何人都能以任何順序戳戳看這個模型。每次點擊就派送對應的動作並重新顯示狀態。
4. **引導情境**：一組**情境**，每個情境一個分頁。每個分頁包含一段簡短的白話情境說明（它設定了什麼狀況、要注意看什麼），下方是這個情境依序要**按的按鈕**。每一步都是真的按鈕：點擊就執行該動作並前進到下一步。開始一個情境時，先重置到已知的初始狀態，讓情境每次都以同樣方式進行。

選擇能展示棘手情況的情境，也就是那些在紙上很難推理的：正常流程、一個刁鑽的邊角情況、一次嘗試做本應不合法的事。

保持美觀但節制：乾淨的字體、寬鬆的間距、一個強調色。不要動畫、不要花招：任何會和狀態與按鈕搶注意力的東西都不要。

### 4. 交給使用者

把檔案傳給他，或幫他打開。他會在有空時點過引導情境和自由操作；有趣的時刻是當他說「等等，這不應該可能發生」或「咦，我以為 X 會不一樣」，那些就是**想法**中的 bug，而這正是重點。如果他想要新的動作或新的情境，就加上去。原型會演進。

### 5. 保存答案與原型

原型回答了它的問題之後，保存答案，再依照 [SKILL](SKILL.md) 所說的方式保存原型。邏輯原型的對應方式：驗證過的 reducer／狀態機／函式集搬進正式模組（決策被吸收）；HTML 外殼跟著進入保存原型作為一手資料的拋棄式分支，由於它是一個自給自足的檔案，在那裡仍然可以輕易重新執行。

## 反模式

- **不要加測試。** 需要測試的原型就不再是原型了。
- **不要接到真正的資料庫。** 除非問題明確是關於持久化，否則用記憶體內的狀態。
- **不要通用化。** 不要有「如果之後想支援 X 呢」。原型只回答一個問題。
- **不要把邏輯和頁面混在一起。** 如果純模組參照了 DOM、`document` 或按鈕處理函式，它就搬不走了。讓頁面只是包在純模組外面的一層薄殼。
- **不要動用框架、打包工具或伺服器。** 一個收件人雙擊就能開的檔案；React app 或開發伺服器會毀掉「可分享」這件事。
- **不要把 HTML 外殼放進正式環境。** 這個頁面是為了讓人手動點過而最佳化的。值得保留的是它背後的邏輯模組。
