# 原型（Prototype）

與使用者溝通、以及原型畫面上給人看的文字，都使用繁體中文。

原型是**用來回答一個問題的拋棄式程式碼**。問題決定它的形狀。

## 選擇分支

根據使用者的提示、周圍的程式碼，或在使用者在場時直接詢問，判斷要回答的是哪一種問題：

- **「這個邏輯／狀態模型合理嗎？」** → [LOGIC.md](LOGIC.md)。做一個可分享的單一 HTML 檔（自由操作的按鈕，加上分頁式的引導情境），把狀態機推過那些在紙上很難推理的情況，而且非開發者也能操作。
- **「這個該長什麼樣子？」** → [UI.md](UI.md)。在同一個路由上產生幾個截然不同的 UI 變體，用 URL 參數和一個浮動的底部列切換。

兩個分支產出的東西非常不同，選錯會浪費整個原型。如果問題真的模稜兩可、使用者又聯絡不上，就選比較符合周圍程式碼的那個分支（後端模組 → 邏輯；頁面或元件 → UI），並在原型最上方寫明這個假設。

## 兩個分支都適用的規則

1. **從第一天起就是拋棄式的，並清楚標示。** 把原型程式碼放在它最終會被使用的地方附近（放在它要模擬的模組或頁面旁邊），讓情境一目了然；但命名要讓隨便瞄一眼的人也看得出這是原型、不是正式程式碼。拋棄式 UI 路由要遵守專案既有的路由慣例；不要發明新的頂層結構。
2. **極易執行。** UI 原型用專案任務工具的一個指令啟動：`python <path>`、`pnpm <name>`、`bun <path>` 等。邏輯展示是一個使用者雙擊就能開的 HTML 檔。無論哪種，都不需要動腦就能啟動。
3. **預設不做持久化。** 狀態放在記憶體。持久化是原型要**檢驗**的東西，而不是它該依賴的東西。如果問題明確牽涉資料庫，就用一個暫存資料庫或本地檔案，並取一個明確的「PROTOTYPE，可刪除」名稱。
4. **略過打磨。** 不寫測試，除了讓原型**能跑**所需之外不做錯誤處理，不做抽象化。重點是快速學到東西。
5. **把狀態攤開來。** 每次操作之後（邏輯），或每次切換變體時（UI），印出或顯示完整的相關狀態，讓使用者看得出什麼改變了。
6. **完成後要保存。** 把驗證過的決策整合進正式程式碼，然後把原型本身當作**一手資料**保存：commit 到一個拋棄式分支（不進 main），並在實作 issue 上留下指向那個分支的情境指標。答案也要保存（結論以及它解決了什麼問題），寫在 issue 或 commit 中。main 分支只保留驗證過的決策。
