# UI 原型

在同一個路由上產生**幾個截然不同的 UI 變體**，用一個浮動的底部列切換。使用者在瀏覽器裡翻看各個變體，挑一個（或從每個變體各拿一點），然後把其他的丟掉。

如果問題是關於邏輯／狀態，而不是長相，那就是走錯分支了。改用 [LOGIC.md](LOGIC.md)。

## 什麼時候該用這個形狀

- 「這個頁面該長什麼樣子？」
- 「在決定之前，我想先看看這個儀表板的幾種做法。」
- 「幫設定畫面試一個不同的版面。」
- 任何使用者原本會花一整天，在腦中三個模糊的草圖之間猶豫的時候。

## 兩種子形狀：強烈偏好 A

當 UI 原型**緊貼著 app 的其他部分**時，會更容易判斷好壞：真實的頁首、真實的側欄、真實的資料、真實的密度。一個孤立的拋棄式路由是真空的：每個變體單獨看都還可以。只要有合理的既有頁面可以承載變體，就預設用子形狀 A。只有當原型真的沒有附近的家時，才用子形狀 B。

### 子形狀 A：調整既有頁面（偏好）

路由已經存在。變體渲染在**同一個路由**上，由 URL 參數 `?variant=` 控制。既有的資料讀取、參數、驗證都保留，只有渲染的部分替換。這是預設；除非有特別理由，否則選它。

如果原型要做的東西還沒有頁面、但**自然會放在某個頁面裡**（儀表板的新區塊、設定畫面的新卡片、既有流程中的新步驟），它仍然是子形狀 A。把變體掛在宿主頁面裡。

### 子形狀 B：新頁面（最後手段）

只有當要模擬的東西真的沒有既有頁面可以放進去時才用（例如一個全新的頂層畫面，或一個無法合理嵌入任何地方的流程）。

依照專案既有的路由慣例建立一個**拋棄式路由**。不要發明新的頂層結構。命名要讓人一看就知道是原型（例如在路徑或檔名中包含 `prototype` 這個字）。同樣使用 `?variant=` 模式。

決定用子形狀 B 之前，再確認一次：真的沒有既有頁面可以嵌入嗎？空路由會藏住有資料的頁面才會暴露的設計問題。

兩種子形狀的浮動底部列都一樣。

## Python 專案的對應方式

如果專案的介面是 Python（例如 Streamlit、Flask、Dash），用同樣的概念：同一個頁面、用一個參數或側欄選單切換變體、切換器只在開發模式顯示。下方的 TSX 範例只是示意，依專案實際使用的框架改寫。

## 流程

### 1. 寫明問題並決定 N

預設 **3 個變體**。超過 5 個就不再是截然不同，而開始變成雜訊，所以上限是 5。

用一行寫下計畫，放在原型所在位置或檔案頂端的註解：

> 「設定頁的三個變體，透過 `?variant=` 切換，放在既有的 `/settings` 路由上。」

不論使用者在不在場提出異議，這樣都行得通。

### 2. 產生截然不同的變體

起草每個變體。每一個都要符合：

- 頁面的目的，以及它能取得的資料。
- 專案的元件庫／樣式系統（TailwindCSS、shadcn、MUI、純 CSS、Streamlit 元件，或任何專案在用的）。
- 清楚的匯出元件名稱，例如 `VariantA`、`VariantB`、`VariantC`。

變體必須在**結構上不同**：不同的版面、不同的資訊層級、不同的主要操作方式，而不只是不同的顏色。三個稍微調整過的卡片網格不是 UI 原型，那是壁紙。如果兩份草稿太像，就帶著明確的「不要用卡片網格」指示重做其中一個。

### 3. 把它們接在一起

在路由上建立單一切換元件：

```tsx
// 虛擬碼，依專案的框架改寫
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

子形狀 A（既有頁面）：所有既有的資料讀取都留在切換器上方；每個變體只改變渲染的子樹。

子形狀 B（新頁面）：`/prototype/<name>` 底下的拋棄式路由掛上同一個切換器。

### 4. 建立浮動切換器

一個固定在畫面底部中央的小列，有三個部分：

- **左箭頭**：切換到上一個變體（循環）。
- **變體標籤**：顯示目前的變體代號，若變體有匯出名稱也一併顯示，例如 `B（側欄版面）`。
- **右箭頭**：往下一個切換（循環）。

行為：

- 點擊箭頭時更新 URL 參數（使用框架的路由器，例如 Next 的 `router.replace`、React Router 的 `navigate` 等），讓變體可以分享、重新整理後也不變。
- 鍵盤：`←` 和 `→` 方向鍵也能切換。當 `<input>`、`<textarea>` 或 `[contenteditable]` 有焦點時，不要攔截方向鍵。
- 視覺上和頁面明顯區隔（例如高對比的膠囊形狀、淡淡的陰影），讓人一看就知道它不是被評估的設計的一部分。
- 在正式版中隱藏：以 `process.env.NODE_ENV !== 'production'` 或同等的檢查為條件，避免不小心合併進去的原型把切換列送到使用者面前。

把切換器放在單一共用元件中，讓兩種子形狀都能重用。放在專案存放共用 UI 的地方。

### 5. 交給使用者

給出 URL（以及 `?variant=` 的代號）。使用者會在有空時翻看。最有價值的回饋通常是**「我要 B 的頁首配上 C 的側欄」**，那才是他真正想要的設計。

### 6. 保存答案並清理

某個變體勝出後，保存答案（哪個變體、為什麼），再依照 [SKILL](SKILL.md) 所說的方式保存原型。把勝出者整合進正式程式碼，其他的移到拋棄式分支，而不是留在 main：

- **子形狀 A**：把勝出者整合進既有頁面；從 main 移除落選的變體與切換器。
- **子形狀 B**：把勝出的變體升格為正式路由；從 main 移除拋棄式路由與切換器。

完整的變體組合是一手資料，所以它落在拋棄式分支，而不是垃圾桶；留在 main 的變體元件和切換器很快就會腐爛，並讓下一個讀者困惑。

## 反模式

- **只差在顏色或文案的變體。** 那是微調，不是原型。真正的變體在結構上意見不同。
- **變體之間共用太多程式碼。** 共用一個 `<Header>` 沒問題；共用一個 `<Layout>` 就失去意義了。每個變體都應該能自由丟掉版面。
- **把變體接到真正會寫入資料的操作。** 唯讀的原型沒問題。如果某個變體需要寫入，把它指向一個樁（stub）：問題是「這個該長什麼樣子」，不是「後端能不能動」。
- **直接把原型升格為正式程式碼。** 變體程式碼是在原型限制下寫的（沒有測試、最少的錯誤處理）。整合進去時要好好重寫。
