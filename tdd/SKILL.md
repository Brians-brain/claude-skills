# 測試驅動開發（Test-Driven Development）

全程使用繁體中文與使用者溝通；測試函式名稱用英文 snake_case，讓它讀起來像規格（例如 `test_alternate_with_same_footprint_is_accepted`）。

TDD 就是 red → green 循環。這個 skill 是讓這個循環產出「值得保留的測試」的參考：什麼是好測試、測試該放在哪、有哪些反模式、循環的規則。每一節都適用於每一輪：在循環之前與之中查閱，而不是之後。

探索程式碼時，若有 `GLOSSARY.md` 就先讀，讓測試名稱與介面用詞跟專案的領域語言一致；也要尊重你所修改區域裡的 ADR。

## 預設工具（Python 專案）

- 測試框架：`pytest`（若專案已用 `unittest`，沿用專案既有的）。
- 跑單一測試檔：`pytest tests/test_xxx.py -q`；跑單一測試：`pytest tests/test_xxx.py::test_name -q`。
- 型別檢查：若專案有設定 `mypy` 或 `pyright`，每輪 green 之後跑一次。
- 先看專案根目錄的 `pyproject.toml`、`pytest.ini`、`requirements*.txt`，沿用既有慣例，不要自己發明新的。

## 什麼是好測試

測試透過**公開介面**驗證**行為**，而不是驗證實作細節。程式碼可以整個重寫，測試不該跟著改。好的測試讀起來像規格：「同封裝同規格的料可被接受為替代料」直接告訴你系統具備什麼能力；而且因為它不在乎內部結構，所以能撐過重構。

範例見 [tests.md](tests.md)，mock 的準則見 [mocking.md](mocking.md)。

## Seam：測試放在哪裡

**Seam** 是你測試時使用的公開邊界：在這個介面上，你能觀察到行為而不必伸手進內部。測試只放在 seam 上，絕不針對內部實作。

**只在事先約定好的 seam 上寫測試。** 寫任何測試之前，先列出要測的 seam，並跟使用者確認。未經確認的 seam 上不寫任何測試。你不可能測所有東西，事先約定 seam，才能讓測試的心力落在關鍵路徑與複雜邏輯上，而不是每個邊角情況。

問使用者：「公開介面是什麼？我們要在哪些 seam 上測？」每個提議的 seam 附一行說明：它能抓到什麼、抓不到什麼。

當介面本身的形狀還有疑問時（模組要多深、seam 該放哪裡、介面該暴露什麼），用 Skill tool 呼叫 "codebase-design" 取得詞彙。它是模組、介面、深度、seam、轉接器、槓桿與局部性這些術語的共同來源，是拿來查閱的參考，而不是要執行的一個 session。

## 反模式

- **綁死實作**：mock 內部協作者、測試私有函式（`_xxx`），或透過旁路驗證（直接查資料庫，而不是透過介面讀回）。徵兆：行為沒變，重構後測試卻壞了。
- **套套邏輯（Tautological）**：斷言用和程式碼一樣的方法重算期望值（例如 `assert add(a, b) == a + b`、用同樣算法手動產生的快照、常數斷言等於自己），所以必然通過，永遠不可能和程式碼意見不同。期望值必須來自獨立的真實來源：已知正確的字面值、手算過的範例、規格書。
- **水平切片**：先寫完所有測試，再寫所有實作。大量預先寫好的測試驗證的是**想像中**的行為：你測的是東西的**形狀**而不是使用者面對的行為，測試會對真正的改變不敏感，而且你在理解實作之前就把測試結構定死了。改用**垂直切片**：一個測試 → 一段實作 → 重複，每個測試都是一發 **tracer bullet（曳光彈）**，回應上一輪學到的東西。

## 循環規則

- **先紅再綠。** 先寫一個會失敗的測試，並**實際執行看到它失敗**，再只寫剛好讓它通過的程式碼。不要預先應付未來的測試，也不要加推測性的功能。
- **一次一個切片。** 每一輪：一個 seam、一個測試、一段最小實作。
- **重構不屬於這個循環。** 重構屬於審查階段（見 `code-review-zh` skill），不屬於 red → green 的實作循環。
