與使用者溝通、以及 spec 本身，都使用繁體中文撰寫；模組名稱、型別、指令維持原文。

這個 skill 根據目前對話的情境與對程式碼的理解，產出一份 spec。**不要**訪談使用者；只綜合你已經知道的內容。

Issue tracker 與 triage 標籤用語應該已經提供給你了。如果沒有，告訴使用者先執行 `/setup-matt-pocock-skills`。

## 流程

1. 如果你還沒探索過 repo，先探索，了解程式碼的現況。整份 spec 都使用專案術語表的用語，並尊重你所修改區域裡的 ADR。

2. 勾勒你要在哪些 seam 上測試這個功能。既有的 seam 優先於新的 seam。使用盡可能高的 seam。如果需要新的 seam，盡量把它提在最高的位置。整個程式碼中的 seam 越少越好，理想數量是一個。

跟使用者確認這些 seam 符合他的預期。

3. 用下方範本撰寫 spec，然後發布到專案的 issue tracker。套用 `ready-for-agent` triage 標籤，不需要再額外 triage。

<spec-template>

## 問題陳述

使用者面對的問題，從使用者的角度描述。

## 解決方案

問題的解決方案，從使用者的角度描述。

## 使用者故事

一份**很長**的、編號的使用者故事清單。每個使用者故事的格式為：

1. 身為 <角色>，我想要 <功能>，以便 <好處>

<user-story-example>
1. 身為採購人員，我想要看到每顆料可用的替代料與其價差，以便在原料缺貨時快速做出替換決定
</user-story-example>

這份清單應該極為詳盡，涵蓋功能的所有面向。

## 實作決策

已經做出的實作決策清單。可以包括：

- 要建立／修改的模組
- 這些模組中要修改的介面
- 開發者提供的技術說明
- 架構決策
- 資料結構（schema）變更
- API 契約
- 特定的互動方式

**不要**包含具體的檔案路徑或程式碼片段，它們很快就會過時。

例外：如果原型產出的片段比文字更精確地表達了某個決策（狀態機、reducer、schema、型別形狀），就把它內嵌在相關決策中，並簡短註明它來自原型。只保留富含決策的部分，不要一個能跑的展示，只要重點。

## 測試決策

已經做出的測試決策清單。包括：

- 什麼是好測試的描述（只測外部行為，不測實作細節）
- 哪些模組會被測試
- 測試的既有範例（也就是程式碼中類似的測試）

## 不在範圍內

這份 spec 不涵蓋的東西。

## 其他備註

關於這個功能的任何其他備註。

</spec-template>
