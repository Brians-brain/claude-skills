# 拆成 Ticket

與使用者溝通、以及 ticket 本身，都使用繁體中文撰寫。

把一份計畫、spec 或對話拆成一組 **ticket**：tracer-bullet（曳光彈）式的垂直切片，每張都標明哪些 ticket **阻擋**它。

Issue tracker 與 triage 標籤用語應該已經提供給你了。如果沒有，告訴使用者先執行 `/setup-matt-pocock-skills`。

## 流程

### 1. 收集情境

以對話中已有的內容為基礎工作。如果使用者以參數傳入一個參照（spec 路徑、issue 編號或 URL），取得它並閱讀完整內文與留言。

### 2. 探索程式碼（選用）

如果你還沒探索過程式碼，先探索，了解程式碼的現況。ticket 的標題與描述要使用專案術語表的用語，並尊重你所修改區域裡的 ADR。

尋找可以先做「預先重構（prefactor）」讓實作更容易的機會。「先讓改變變容易，再做那個容易的改變。」

### 3. 起草垂直切片

把工作拆成 **tracer bullet** ticket。

<vertical-slice-rules>

- 每個切片切出一條窄但**完整**的路徑，貫穿每一層（資料結構、API、UI、測試）：是垂直的，**不是**某一層的水平切片
- 一個完成的切片可以單獨展示或驗證
- 每個切片的大小要能放進一個全新的情境視窗
- 任何預先重構都要先做

</vertical-slice-rules>

為每張 ticket 標明它的**阻擋邊**：必須先完成、它才能開始的其他 ticket。沒有阻擋者的 ticket 可以立刻開始。

**大範圍重構是垂直切片的例外。** **大範圍重構**是一個機械性的變更（重新命名一個欄位、改變一個共用符號的型別），它的**影響範圍**擴散到整個程式碼，所以單一修改就會一次弄壞成千上萬個呼叫處，沒有任何垂直切片能保持全綠。不要硬把它塞成 tracer bullet；改用**擴張—收縮（expand–contract）**排序。先擴張：在舊形式旁邊加上新形式，讓什麼都不會壞。然後依影響範圍分批遷移呼叫處（每個套件、每個目錄），每一批是一張自己的 ticket，被「擴張」那張阻擋；因為舊形式還在，每一批之間 CI 都能保持綠燈。最後收縮：當沒有任何呼叫端還在用舊形式時刪掉它，這張 ticket 被每一批遷移阻擋。如果連各批次都無法單獨保持綠燈，就保留這個順序，但讓它們共用一條整合分支，全部阻擋最後一張「整合並驗證」的 ticket；只有在那裡才保證綠燈。

### 4. 向使用者確認

把提議的拆分以編號清單呈現。每張 ticket 顯示：

- **標題**：簡短的描述性名稱
- **被誰阻擋**：哪些其他 ticket（如果有）必須先完成
- **交付什麼**：這張 ticket 讓哪個端到端的行為變得可用

問使用者：

- 粒度感覺對嗎？（太粗／太細）
- 阻擋關係正確嗎：每張 ticket 是否只依賴真正卡住它的 ticket？
- 有沒有 ticket 應該合併或再拆細？

反覆修改，直到使用者核可這份拆分。

### 5. 把 ticket 發布到設定好的 tracker

發布核可的 ticket。**怎麼**發布取決於 `/setup-matt-pocock-skills` 設定的 tracker；兩種方式的 ticket 內容一樣，只有阻擋邊的形式不同：

- **本地檔案** → 每張 ticket 寫一個檔案，放在 `.scratch/<feature-slug>/issues/<NN>-<slug>.md`，依相依順序（阻擋者優先）從 `01` 開始編號。每個檔案的「被誰阻擋」列出它依賴的編號／標題。使用下方的單張 ticket 檔案範本：一個檔案一張 ticket，絕不合併成單一檔案。
- **真正的 issue tracker（GitHub、Linear……）** → 依相依順序（阻擋者優先）每張 ticket 發布一個 issue，讓每張 ticket 的阻擋邊能參照真實的識別碼。如果平台有原生的阻擋關係就使用它；否則把每張 ticket 的「被誰阻擋」設為阻擋它的 issue。如果來源是一個既有的 issue，把每張 ticket 設為它的子 issue（tracker 文件中的操作）。除非另有指示，否則套用 `ready-for-agent` triage 標籤；這些 ticket 在設計上就是可以讓 agent 直接接手的。

處理**前沿**：任何阻擋者都已完成的 ticket。如果是純線性的鏈，就是由上而下。

**不要**關閉或修改任何父 issue。
