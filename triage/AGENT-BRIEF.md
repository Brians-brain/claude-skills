# 撰寫 Agent 簡報

Agent 簡報是 GitHub issue 或 PR 移到 `ready-for-agent` 時發布的一則結構化留言（以繁體中文撰寫；型別、函式、指令維持原文）。它是無人看管的 agent 工作時所依據的權威規格。原始內文與討論只是背景：agent 簡報才是合約。

簡報說明 **agent 應該做什麼**，涵蓋兩種情況：如果是 issue，就是從零開始做出這個變更；如果是 PR，就是**對既有的 diff** 還需要做什麼：完成它、補上缺口、處理審查意見。兩種情況原則相同；下方的 PR 範例顯示了差異。

## 原則

### 耐久勝過精確

Issue 可能在 `ready-for-agent` 停留好幾天甚至幾週，這段期間程式碼會改變。撰寫簡報時，要讓它在檔案被重新命名、移動或重構之後仍然有用。

- **要**描述介面、型別與行為契約
- **要**點名 agent 應該尋找或修改的具體型別、函式簽章或設定形狀
- **不要**引用檔案路徑：它們會過時
- **不要**引用行號
- **不要**假設目前的實作結構會保持不變

### 描述行為，不描述程序

描述系統**應該做什麼**，而不是**怎麼實作**。Agent 會重新探索程式碼，並自己做實作決策。

- **好：**「`PriceQuery` 型別應該接受一個選填的 `currency` 欄位，型別為 `CurrencyCode`」
- **壞：**「打開 src/costing/query.py，在第 42 行加一個 currency 欄位」
- **好：**「當使用者執行 `bom-cost` 而沒有給參數時，應該顯示用法說明」
- **壞：**「在 main 函式裡加一個 if 判斷」

### 完整的驗收條件

Agent 需要知道什麼時候算完成。每份 agent 簡報都必須有具體、可測試的驗收條件。每一條都應該能獨立驗證。

- **好：**「對同一份 BOM 執行兩次，第二次不會再呼叫經銷商 API（從快取讀取）」
- **壞：**「快取應該正常運作」

### 明確的範圍邊界

說明什麼不在範圍內。這能防止 agent 鍍金，或對相鄰功能做出假設。

## 範本

```markdown
## Agent 簡報

**類別：** bug / enhancement
**摘要：** 一行描述需要發生什麼

**目前行為：**
描述現在發生什麼。若是 bug，就是壞掉的行為。
若是 enhancement，就是新功能所要建立在其上的現況。

**期望行為：**
描述 agent 的工作完成後應該發生什麼。
具體說明邊角情況與錯誤狀況。

**關鍵介面：**
- `TypeName`：需要改變什麼、為什麼
- `function_name()` 的回傳型別：目前回傳什麼、應該回傳什麼
- 設定形狀：需要的任何新設定選項

**驗收條件：**
- [ ] 具體、可測試的條件 1
- [ ] 具體、可測試的條件 2
- [ ] 具體、可測試的條件 3

**不在範圍內：**
- 這個 issue 中**不應該**被修改或處理的東西
- 看似相關、但其實是獨立的相鄰功能
```

## 範例

### 好的 agent 簡報（bug）

```markdown
## Agent 簡報

**類別：** bug
**摘要：** 訂購數量剛好等於價格級距下限時，取到錯誤的單價

**目前行為：**
當訂購數量剛好等於某個價格級距的最小數量時（例如級距為 1000 起，
訂購 1000），成本計算取的是上一個級距的單價，導致成本被高估。

**期望行為：**
訂購數量大於或等於某級距的最小數量時，就適用該級距的單價。

**關鍵介面：**
- `unit_price_for(breaks, qty)`：回傳型別不變，但選擇級距的比較
  需要包含等於的情況
- 任何讀取經銷商價格級距並建立 `PriceBreak` 清單的函式

**驗收條件：**
- [ ] 數量小於第一個級距下限時，回傳第一個級距的單價
- [ ] 數量剛好等於某級距下限時，回傳該級距的單價
- [ ] 數量介於兩個級距之間時，回傳較低級距的單價
- [ ] 既有的成本計算測試全部通過

**不在範圍內：**
- 改變價格級距的資料來源
- 幣別換算
```

### 好的 agent 簡報（enhancement）

```markdown
## Agent 簡報

**類別：** enhancement
**摘要：** 新增 `.out-of-scope/` 目錄支援，用來追蹤被拒絕的功能請求

**目前行為：**
功能請求被拒絕時，issue 會被標上 `wontfix` 並關閉、附上一則留言。
沒有任何關於這個決策或理由的持久紀錄。之後類似的請求，
需要維護者自己回想或搜尋先前的討論。

**期望行為：**
被拒絕的功能請求應該記錄在 `.out-of-scope/<concept>.md` 檔案中，
包含決策、理由，以及所有請求過該功能的 issue 連結。
Triage 新 issue 時，應該檢查這些檔案是否有相符的紀錄。

**關鍵介面：**
- `.out-of-scope/` 中的 Markdown 檔案格式：每個檔案應該有一個
  `# 概念名稱` 標題、一行 `**決策：**`、一行 `**理由：**`，
  以及一份附 issue 連結的 `**先前的請求：**` 清單
- Triage 流程應該在早期讀取所有 `.out-of-scope/*.md` 檔案，
  並依概念相似度比對新進的 issue

**驗收條件：**
- [ ] 以 wontfix 關閉一個功能時，會建立或更新 `.out-of-scope/` 中的檔案
- [ ] 檔案包含決策、理由，以及被關閉 issue 的連結
- [ ] 如果已經有相符的 `.out-of-scope/` 檔案，新 issue 會被附加到
      它的「先前的請求」清單，而不是建立重複的檔案
- [ ] Triage 時會檢查既有的 `.out-of-scope/` 檔案，並在新 issue
      與先前的拒絕相符時提出來

**不在範圍內：**
- 自動比對（由人確認是否相符）
- 重新開啟先前被拒絕的功能
- Bug 回報（只有 enhancement 的拒絕會進入 `.out-of-scope/`）
```

### 好的 agent 簡報（PR）

若是 PR，「目前行為」描述的是 diff 的狀態，簡報要求 agent 完成或修正它，而不是從零開始。

```markdown
## Agent 簡報

**類別：** enhancement
**摘要：** 完成貢獻者為 `bom-cost` 加上的 `--json` 輸出選項

**目前行為：**
這個 PR 加入了一個 `--json` 選項，把成本結果序列化成 JSON。
正常流程可以運作，diff 也符合專案的指令結構。還剩兩個缺口：
錯誤訊息仍然以一般文字輸出（不是 JSON），而且新選項沒有測試。

**期望行為：**
使用 `--json` 時，所有輸出（包括錯誤）都是 stdout 上格式正確的 JSON，
指令的結束碼不變。沒有加這個選項時，既有的人類可讀輸出完全不受影響。

**關鍵介面：**
- 指令的錯誤路徑在 `--json` 下應該輸出 `{ "error": string }`，
  而不是一般文字的錯誤
- 沿用 PR 已經加入的序列化函式；不要再引入第二個

**驗收條件：**
- [ ] `bom-cost --json` 在成功與錯誤兩種情況都輸出有效的 JSON
- [ ] 結束碼與非 JSON 的指令一致
- [ ] 有一個測試涵蓋 `--json` 的成功輸出，以及一種錯誤情況
- [ ] 預設（非 JSON）輸出逐位元組不變

**不在範圍內：**
- 為其他指令加上 `--json`
- 改變 PR 已經定義的成功結果 JSON 形狀
```

### 壞的 agent 簡報

```markdown
## Agent 簡報

**摘要：** 修 triage 的 bug

**要做什麼：**
triage 那個東西壞了。去看主檔案然後修好它。
大概在第 150 行附近的函式有問題。

**要改的檔案：**
- src/triage/handler.py（第 150 行）
- src/types.py（第 42 行）
```

這份很糟，因為：
- 沒有類別
- 描述含糊（「triage 那個東西壞了」）
- 引用了會過時的檔案路徑與行號
- 沒有驗收條件
- 沒有範圍邊界
- 沒有描述目前行為與期望行為
