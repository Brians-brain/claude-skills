一個鬆散的想法來了，大到一個 agent session 裝不下，而且籠罩在迷霧中：從這裡到**目的地**的路還看不見。Wayfinding（找路）是要找到那條路，而不是直衝目的地。這個 skill 在 repo 的 issue tracker 上把路畫成一張**共享地圖**，然後一次處理一張**決策 ticket**（解決之後產生的是一個決策的問題，而不是要執行的建置切片），直到路線變清楚。

每個專案的目的地都不同，而命名目的地是畫地圖的第一步：它會形塑每一張 ticket。它可能是一份要交出去並反覆修改的 spec、一個必須在開始規劃前鎖定的決策，或一個就地進行的改變（例如資料結構遷移）。地圖不限領域：工程工作、課程內容，任何符合這個形狀的東西都可以。

## 規劃，不執行

Wayfinder 預設是**規劃**：每張 ticket 解決一個決策，當路變清楚、在有人動手做之前沒有任何東西還需要決定時，地圖就完成了。「乾脆直接做」的衝動，通常代表你已經走到地圖的邊緣，該交棒了。一個專案可以在它的 **Notes** 中覆寫這一點，把執行也帶進地圖本身；但如果沒有，就只產出決策，不產出成品。

## 用名稱稱呼

每張地圖和 ticket 都是一個 issue，所以它有一個**名稱**：它的標題。在所有給人讀的內容中（敘述、地圖的 Decisions-so-far），都用名稱稱呼它，絕不用單獨的 id、編號或 slug。一整排 `#42, #43, #44` 無法閱讀；名稱一眼就懂。id 和 URL 不會消失；名稱包住它的連結，但它們放在名稱**裡面**，而不是取代名稱。

## 地圖

地圖是這個 repo 的 issue tracker 上的單一 issue，標上 `wayfinder:map` 標籤，是標準的產出物。它的 ticket 是地圖的子 issue。

地圖是**索引**，不是倉庫。它列出已做的決策，並指向保存細節的 ticket；一個決策只存在一個地方，也就是它的 ticket，所以地圖從不重述它，只寫摘要並附連結。

**地圖、子 ticket、阻擋關係與前沿查詢實際放在哪裡，取決於 tracker。** Issue tracker 應該已經提供給你了。如果沒有，告訴使用者先執行 `/setup-matt-pocock-skills`。查閱 tracker 文件的「Wayfinding 操作」段落，了解**這個** repo 如何表達它們。如果沒有提供任何 tracker，預設使用本地 markdown tracker。

### 地圖內文

整張地圖的低解析度版本，每個 session 載入一次。未關閉的 ticket **不**列在這裡：它們是未關閉的子 issue，透過查詢找到。

```markdown
## 目的地

<走到這張地圖的盡頭是什麼樣子：這個專案要找路前往的 spec、決策或改變。一到兩行；每個 session 在選 ticket 之前都先以它定位。>

## Notes

<領域；每個 session 都應該參考的 skill；這個專案的固定偏好>

## Decisions so far

<!-- 索引：每張已關閉的 ticket 一行，足以判斷是否相關，需要細節時再點進連結看 ticket -->

- [<已關閉的 ticket 標題>](連結)：<答案的一行摘要>

## 尚未具體化

<!-- 見「戰爭迷霧」：範圍內但還無法開成 ticket 的迷霧；隨著前沿推進而畢業 -->
```

### Ticket

每張 ticket 都是地圖的一個**子 issue**；tracker 的 issue id 就是它的身分。它的內文是一個問題，大小適合一個 10 萬 token 的 agent session：

```markdown
## 問題

<這張 ticket 要解決的決策或調查>
```

每張 ticket 帶有一個 `wayfinder:<type>` 標籤，為 `research`、`prototype`、`grilling`、`task` 其中之一（見 [Ticket 類型](#ticket-類型)）。地圖和它的 ticket 只帶 `wayfinder:` 標籤，絕不帶 `ready-for-agent` 這類 triage 標籤：它們是決策，不是實作工作。

一個 session 在做任何工作**之前**，**先**把 ticket 指派給推進這張地圖的開發者來**認領**它，讓同時進行的其他 session 會跳過它。那個指派人**就是**認領：未關閉、未指派的 ticket 就是未被認領的。

阻擋關係使用 tracker **原生**的相依關係：這很重要，因為它會在 tracker 自己的 UI 上**視覺化地**呈現前沿，讓人不用打開地圖就看得到哪些可以接手。只有在 tracker 沒有原生阻擋功能時，才退而使用內文慣例。當所有阻擋一張 ticket 的 ticket 都關閉時，它就**解除阻擋**；**前沿**是未關閉、未被阻擋、未被認領的子 issue，也就是已知世界的邊緣。

答案不屬於內文；它在解決時記錄（見[走過地圖](#走過地圖)）。解決 ticket 時建立的資產從 issue 連結過去，而不是直接貼進來。

## Ticket 類型

每張 ticket 不是 **HITL**（人在迴路中，**與**一個親自發言的人一起進行），就是 **AFK**（由 agent 單獨推進）。HITL ticket 只能透過那個即時交流來解決；agent 永遠不能代替人回答他那一方（一個自問自答的拷問 agent 就違反了這一點）。

- **Research（研究）**（AFK）：閱讀文件、第三方 API 或知識庫等本地資源，找出某個決策在等的事實。由一個用 Skill tool 呼叫 "research" 的子 agent 解決。當需要目前工作目錄之外的知識時使用。
- **Prototype（原型）**（HITL）：用 Skill tool 呼叫 "prototype"，做一個便宜、粗糙、具體、可以讓人反應的東西（大綱、草稿、樁，或 UI／邏輯程式碼），提高討論的精確度。把原型作為資產連結過去。當「它該長什麼樣」或「它該怎麼運作」是關鍵問題時使用。
- **Grilling（拷問）**（HITL）：對話。預設的類型。永遠用 Skill tool 呼叫兩次，分別是 "grilling" 和 "domain-modeling"。
- **Task（任務）**（HITL 或 AFK）：在做出某個**決策**之前必須先完成的手動工作：沒有東西要決定、要做原型或要研究，但討論被它卡住，直到它完成。例如註冊某個服務以便評估它的 API、開通存取權限、搬移資料以便看清它的形狀。這是唯一一種**做事**而不是做決策的類型，它存在的理由是解除某個決策的阻擋，而不是交付目的地。agent 能單獨推進就單獨推進（AFK）；否則就交給人一份精確的檢查清單（HITL）。工作完成時就算解決；答案記錄做了什麼，以及之後的 ticket 依賴的任何結果事實（憑證存放位置、新 URL、資料筆數）。

## 戰爭迷霧

地圖**刻意**不完整：不要畫你還看不見的東西。在現有的 ticket 之外是**戰爭迷霧**：你看得出即將到來、但因為還依賴尚未解決的問題而無法確定的決策與調查的模糊景象。解決一張 ticket 會清除它前方的迷霧，把現在能具體化的東西一張一張地畢業成新 ticket，直到通往目的地的路變清楚、沒有 ticket 剩下。

地圖的**尚未具體化**段落就是寫下那片模糊景象的地方：猜測中的問題、之後要回頭看的區域。它是**朝向**目的地的未知前沿：這裡的一切都在範圍內，只是還不夠清楚，無法開成 ticket。看得多清楚就寫多鬆散或多完整；它同時也是一個路標，讓協作者看得出這個專案往哪裡走。

**迷霧還是 ticket？** 判準是你**現在**能不能精確地說出這個問題，**而不是**你現在能不能回答它。

- **開成 ticket**：當問題已經很清楚，即使它被阻擋、你還無法著手。
- **放進尚未具體化**：當你還無法把它說得那麼清楚。不要預先把迷霧切成 ticket 大小的碎片：它比 ticket 粗，一塊迷霧在前沿抵達時，可能畢業成好幾張 ticket，也可能一張都沒有。

**尚未具體化**不包括已經決定的事（Decisions so far）、已經是現有 ticket 的事，以及不在範圍內的事（下一節）。

## 不在範圍內

迷霧只會**朝向**目的地聚集。目的地決定了範圍，所以超出目的地的工作是**不在範圍內**：它不是迷霧，也不屬於**尚未具體化**。它在地圖上有自己的**不在範圍內**段落：你有意識地排除在**這個**專案之外的工作。讓它落在這裡的是範圍，而不是清晰度。

不在範圍內的工作永不畢業（前沿止於目的地），所以只有在目的地重新劃定時它才會回來，而且是作為一個新專案，而不是接續。

把某件事判定為不在範圍內是一個界定範圍的動作，而不是路線上的一步。當一張既有的 ticket 被發現位於目的地之外（畫地圖時誤劃進範圍，或被某個解決結果暴露出來），**關閉它**（已關閉的 ticket 明確地不在前沿上），並在**不在範圍內**段落留下一行：摘要加上為什麼不在範圍內，並連結那張已關閉的 ticket。它不放進記錄實際走過路線的 **Decisions so far**；範圍邊界不是路線上的一步。

## 呼叫方式

兩種模式。無論哪種，**每個 session 解決的 ticket 都不超過一張**，研究 ticket 例外。

### 畫地圖

使用者帶著一個鬆散的想法呼叫。

1. **命名目的地。** 用 Skill tool 呼叫兩次，分別是 "grilling" 和 "domain-modeling"，確定這張地圖要找路前往的是什麼：spec、決策或改變。目的地決定範圍，所以要先確定。
2. **畫出前沿。** 再拷問一次，這次是**廣度優先**：橫向展開整個空間，而不是在某一條線上深入，找出待決的決策，以及現在就能走的第一步。**如果這沒有找出任何迷霧**（通往目的地的路已經很清楚，整趟旅程小到一個 session 就做得完），你就不需要地圖。停下來，問使用者想怎麼進行。
3. **建立地圖**（標籤 `wayfinder:map`）：填好目的地與 Notes，Decisions-so-far 留空，把迷霧勾勒進**尚未具體化**。
4. **建立你現在能具體化的 ticket**，作為地圖的子 issue，然後在**第二輪**接上阻擋邊（issue 需要先有 id 才能互相參照）。交叉參照也在那一輪用真實的 id 寫：佔位用的 `#<n>` 會自動連到一個無關的 issue。接線會把它們分成前沿和被阻擋的；所有你還無法具體化的東西都留在迷霧裡，也就是**尚未具體化**段落。
5. **派出研究子 agent。** 對你剛建立的每張 `research` ticket，開一個用 Skill tool 呼叫 "research" 的子 agent 平行解決它，把發現保存在一個拋棄式的 `research/<name>` 分支上，並從 ticket 放一個情境指標過去。push 這個分支，但不開 PR：它永遠不會被合併。
6. 停下來：畫地圖就是一個 session 的工作；它不手動解決任何 ticket。

### 走過地圖

使用者帶著一張地圖（URL 或編號）呼叫。ticket 是**選填**的：如果沒有指定，由你挑下一個決策，而不是使用者。

1. 載入**地圖**：低解析度的視圖，不是每張 ticket 的內文。
2. 選擇 ticket。如果使用者指名了，就用它。否則依序取前沿上的第一張。**認領它**：在任何工作之前把它指派給自己。
3. 依它的 `wayfinder:<type>` 標籤所指的類型來解決它（見 [Ticket 類型](#ticket-類型)）。讀標籤，不要只讀內文：內文從不寫類型。**需要時再放大**：依需要取得任何相關或已關閉 ticket 的完整內文；用 Skill tool 呼叫 `## Notes` 區塊所點名的 skill。有疑慮時，用 Skill tool 呼叫兩次，分別是 "grilling" 和 "domain-modeling"。
4. 記錄解決結果：把答案發成一則**解決留言**、**關閉**這個 issue，並在地圖的 Decisions-so-far **附加一個情境指標**。
5. 加入新浮現的 ticket（先建立再接線）；把答案讓它變得可以具體化的迷霧畢業，並從**尚未具體化**中清掉每一塊已畢業的迷霧，讓它只以新 ticket 的形式存在。如果答案揭露某張 ticket（這張或另一張）位於目的地之外，就**判定它不在範圍內**，而不是在路線上解決它。如果這個決策讓地圖的其他部分失效，就更新或刪除那些 ticket。

使用者可能會平行處理未被阻擋的 ticket，所以要預期其他 session 會同時編輯 tracker。
