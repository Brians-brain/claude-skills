# 精靈（Wizard）

與使用者溝通、以及精靈中顯示給人看的指示，都使用繁體中文；變數名稱、指令、URL 維持原文。

**精靈**是一個 bash 腳本，一步一步帶人完成一個手動程序：這種程序手動做很繁瑣，每次重新跟 AI 解釋也很繁瑣。它會打開每個 URL、說清楚要點什麼、複製什麼，擷取這些值，把它們寫到該放的地方（`.env`、GitHub secrets），在每個階段確認，並顯示還剩幾個階段。它可能用來設定第三方服務、執行一次性遷移，或把專案從一個狀態移到另一個狀態。

好用的使用者體驗已經由 [template.sh](template.sh) 解決了：逐階段的進度、確認關卡、跨平台的開啟 URL（包含 WSL）、隱藏的機密輸入、冪等的 `.env` 更新、`gh secret`／`gh variable` 寫入，以及結尾摘要。**你的工作只是界定程序範圍並撰寫它的各個階段。**`STAGES` 標記以上的函式庫在每個精靈中都一樣；這種一致性正是重點：永遠不要手動修改它。

精靈預設是一次性的：為一次執行而建，存在暫存或 `scripts/` 路徑，工作完成後就刪除。只有當使用者想要一條能留在 repo 裡、可重複的設定流程時，才 commit 它。

在 Windows 上，精靈需要在 Git Bash 或 WSL 中執行；交給使用者時要說明這一點。

## 流程

### 1. 界定程序範圍

找出人必須做的每一個手動步驟，以及過程中要擷取的每一個值。先讀 repo，不要憑空問：

- 如果是設定：`.env`、`.env.example`、`.env.*`、`README`、`docker-compose*`、框架設定，以及 `.github/workflows/*`（每一個 `secrets.*`／`vars.*` 參照都是精靈必須產出的值）。
- 如果是遷移或轉換：目前狀態、目標狀態，以及兩者之間不可逆的動作。

然後把有順序的階段清單、以及每個階段產出的值給使用者看，並確認：他可能會增加、刪除或重新排序。

**完成條件：** 每個階段都依序命名，而且對每一個擷取的值，你都知道 (a) 人從哪裡取得它、(b) 它寫到哪裡（`.env`、GitHub secret、兩者，或都不寫；有些階段只是動作）、(c) 它是不是機密（隱藏輸入）還是公開的。

### 2. 畫出每個階段的路徑

為每個階段寫下人要走的精確路徑：打開哪個 URL、在那裡做什麼、值顯示在哪裡、它要填入哪個變數。例如：「後台 → 開發者 → API keys → 顯示測試金鑰 → 複製」。如果你其實不知道目前的介面或確切的指令，就直說，並詢問使用者或查文件：絕不要發明可能不存在的步驟。

**完成條件：** 每個階段都能追溯到一個陌生人也能照著做的具體指示。

### 3. 撰寫精靈

把 `template.sh` 複製到目標路徑。把範例階段換成每個步驟一個 `stage`，依相依順序排列。使用函式庫的輔助函式：`stage`、`say`／`step`、`open_url`、`ask`／`ask_secret`、`write_env`、`set_secret`／`set_var`、`pause`／`confirm`。把 `TOTAL_STAGES` 設為你寫的階段數。

達到範本設定的標準：先打開 URL 再要求它的值、任何機密都用 `ask_secret`、每個要保存的值都 `write_env`、只有 CI 真正需要的值才 `set_secret`、任何不可逆的動作之前都要 `confirm`。每個 `stage` 都會清空畫面，只顯示目前的步驟：讓一個階段只做一件聚焦的事，這樣人需要的資訊不會被捲走。不要碰標記以上的函式庫。

### 4. 驗證並交付

- 執行 `bash -n <script>`；如果有 `shellcheck` 就也跑一次。
- `chmod +x <script>`。
- 不要自己從頭到尾執行它：它會打開瀏覽器，並等待人的輸入。改用靜態追蹤：步驟 1 中的每個值都會被擷取，並落在步驟 1 說的地方；每個 `set_secret` 的名稱都和 CI 中的 `secrets.*` 參照完全一致。
- 告訴使用者如何執行它。如果它是可重複的設定流程，commit 它，並從 README 連結過去，讓下一個人直接執行腳本，而不是去問 AI。
